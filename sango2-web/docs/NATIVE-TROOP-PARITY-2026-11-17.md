## 原版证据

基准 EXE SHA256：`1098558aaea96ae552753df786a8d3910df08fda11c8219dfa133ca001d8e419`。

| 地址 | 核实规则 |
|---|---|
| `0x409FB6` | 现役容量：20级以下为等级×5，20级起100。原函数对-1级返回-5；Web部署适配为0，纯函数保留原值 |
| `0x409FD8` | 预备容量：`clamp((等级-20)*5,0,100)`；40级满编为100现役+100预备 |
| `0x443498` / `0x442EFA` | 两类兵员各自限制容量后都在开战时部署 |
| `0x442D38` | 现役标志2、预备标志4；分队部署顺序1、3、4、5、2，各分队先预备后现役 |
| `0x404A10` / `0x404D18` | 使用`0x485DA8`的33行编制权重；累计整数舍入。现役余数归分队1，预备余数归分队2；不是五队平均分配 |
| `0x406499` / `0x406501` | 现役对象100–112/120–132；预备对象140–152/160–172 |
| `0x403D2F` / `0x403E6D` | 选将/选阵人数使用现役+预备；超编兼容数量不进入这些输入 |

`web-port-research/tools/native_troop_oracle.py`直接执行上述容量、分队人数及对象映射机器码，不替换被测函数。输出101组容量、680组分队人数、26组对象映射，共807组；覆盖-1至99级、34个阵形编号（33为越界返回0）、零/奇数/边界人数及双边13兵种。原始向量在研究目录`evidence/ai/native-troop-vectors.json`，核心测试副本在`packages/core/fixtures/`。

## 接入行为

- 新战斗最多部署每方200兵；等级决定两类上限。曹操初期2级只能部署10名现役兵；演武按真实等级容量配兵，不再凭空给每位将领100兵。
- 每个战场兵员保存`nativeReserve`，命中/伤害使用此前原生普攻内核中的预备兵分支。转换器补出26个预备兵对象和独立`reserveSoldierAttack`事件，演武更换兵种时同步更换两类攻击时序。现有导出总计214对象、5114源帧。
- 喝声在开战时分别减少现役和预备兵；133人示例为100现役+33预备，初级喝声后75+25，不能把预备兵留在后方。保存后不会重施一次。
- 轮战成员与战役武将均保存`troopSlots`。伤亡、撤退、战后回写、JSON保存、再次出征均保留两类人数，避免存活预备兵被重新填到现役槽。
- 战役AI读取同一容量适配器和保存的两类人数，不再把低等级武将超编兵员算作预备兵；兵力就绪判断与战场部署使用一致人数。
- HUD显示仍在场的兵员；两军名册分别显示在场、现役、预备、超编留营。全队余兵仍包含留营和已撤离但存活的人数。
- 高等级技能较多时，战场Grid显式限制列宽，按钮按容器换行；不靠裁切隐藏溢出的指令。手机和桌面均验证双方200兵及全部可见按钮的命中区域。

## 兼容适配及尚未对齐

1. **初始/手动配兵不是原版模型。** 现有战役仍按每位武将80兵初始化。只有聚合总数而无两类状态时，按现役优先分配到等级容量，超出部分保留场外。这防止旧档兵员被静默丢弃，但“超编留营”不是原版新增玩法。手动征兵、重新配兵或暂定AI自动结算改变聚合总数时会重新适配；总数未变则保留已知分类。
2. **旧战中存档保留旧增援方式。** 没有`troopDeployment`字段的正在进行战斗不重排位置/单位、不重置时钟；原先增援入口等待空位的兼容回归仍保留。进入下一阵或重新选将创建新部署。旧存档没有预备攻击时序时使用原有现役时序兜底。
3. **分队人数不等于位置对齐。** 原版部署五个分队，Web仍只提供前军/后军/主将命令，将分队3/4/5合并至前军；横列阵也未建立原版阵形对应。超过100兵采用14行和0.75倍兵员尺度保证显示，属于Web可读性适配，不能算原版坐标。
4. **原版网格与随机调用仍有缺口。** `0x43AF7A`网格寻址以71为行跨度；战术输入的55×14投影和连续移动尚未改为原网格。`0x43DB0D`/`0x43DA1A`预备兵死亡对象以及`0x43DC56`死亡动画涉及随机消耗，本轮未接入。因此虽然普攻/AI共用随机状态，整场调用序列仍不等价。
5. 完整武将技、其余军师技、敌方之间的原版战斗结算、战略链表变化及同一SAV逐帧对照仍未完成。
