# 双向配兵、退兵与补满

Web版补齐了原配兵系统的另一个缺口：武将与城内预备池现在可以**双向调兵**。支持逐兵增减、尽量退回、补满，以及目标人数预览后确认；兵种选择与兵力调配共用同一武将状态，操作后可直接出征或保存。

**原规则的关键是两方向都先调整现役兵，再调整预备兵。** 退兵不会优先退预备兵；城市预备池满时停止接收，兵员继续留在武将手中。补兵受城内存量与武将两兵槽上限约束，不凭空增加兵员，不重复扣征募费，也不占年度行动。

![配兵与满池退兵](screenshots/troop-transfer-1440.png)

截图来自测试存档：40级曹操，最初现役2/预备5，城市预备池149/150；执行“尽量退回”后，只退回1名现役兵，成为现役1/预备5、城内150/150。不是普通开局数值。手机截图见[390宽操作区](screenshots/troop-transfer-390.png)。

## 原机器码依据

EXE SHA-256：`1098558aaea96ae552753df786a8d3910df08fda11c8219dfa133ca001d8e419`。本次使用同一原文件直接执行x86代码，**没有替换任何回调、配兵分支、滑条值运算或随机函数**；内存写钩子只负责观察。

| 原函数 | 已确认规则 | Web对应 |
| --- | --- | --- |
| `0x416366` | 城市 `+134` 预备池达到 `+130` 上限时返回失败；否则优先减武将 `+68` 现役，现役为0后才减 `+72` 预备；城市池加1 | 退回一兵、目标人数减少 |
| `0x416415` | 城市池为0则不补；先补 `+68` 至 `+66` 上限，再补 `+72` 至 `+70` 上限；每补1人城市池减1 | 补充一兵、原有按数量补兵 |
| `0x4164E0`，事件 `0x10000` | 循环调用上面两个原函数，逼近目标；条件不足即把滑条值改回实际可达人数，再调用原 `0x41D9A0` 更新位置 | `policy-troops`、目标人数确认与部分完成反馈 |
| `0x41A6FB` | 待完成标记 `0x4A6424 == 1` 时，先现役后预备补到满槽或空池，并清标记；未开启时无动作 | “补满部队”的最终状态；Web立即完成，不模拟原按住/逐更新临时状态 |
| `0x427A84` 的城市上限更新 | 人口整除2500加110，上限600 | `nativeReserveCapacity()`供自动征募、退兵上限和界面共用 |

例：现役60、预备70，城市池10，目标200，实际只能补到现役70/预备70；随后将目标设为100，会退回40名现役，得到现役30/预备70、城市池40。不会将兵槽自动整理成现役100/预备0。

[反汇编证据](evidence/native-troop-transfer.json)保留退/补兵、完整滑条回调和补满收尾的机器码。原字段与代码对应见 `packages/core/src/native-troops.ts`、`native-policy.ts`。

## 明确的适配与剩余差距

- 原滑条在事件处理中逐步逼近目标；Web滑条和数字框先预览，点击“调整兵力”才提交。快捷增减、退回和补满直接执行。最终兵槽/池状态已有原码依据，输入时序不是逐更新复刻。
- 原补满按钮存在按住标记及逐更新增加，切换窗口时还会调用收尾函数。当前补满直接得到收尾状态，未还原按住时长、窗口切换和动画节奏；不将原临时UI标记写入Web存档。
- 城池/己方在任/非行军/非战斗的Web权限与阶段边界保留既有规则；全部原菜单开放时机和关闭/取消语义仍需客户端连续验证。
- 旧Web存档中超过原两兵槽的营中兵员继续保留；调兵只改变明确的现役/预备人数，不把营中溢出自动当作原预备兵。旧池数量高于当前人口推导上限时，退兵停止，不在此操作里截掉旧池兵员。
- 界面使用原头像与13兵种顺序，整体布局、字体、数字输入和手机排版是Web适配。原640×480窗口、声音与整局连续流程仍未完成一比一验收。

兵种切换不会转换兵员，证据见[原兵种选择](TROOP-SELECTION-2026-11-19.md)。其他漏项继续按[一比一复刻总账](FULL-PARITY-BACKLOG.md)维护。
