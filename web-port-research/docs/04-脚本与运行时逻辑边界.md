# 脚本与运行时逻辑边界

分析日期：2026-11-16。对象是用户提供的 **《三国群英传2 修正版 1.05+》游戏包**，不是英文补丁针对的 Steam 原版。本报告只进行了静态读取与结构检查，没有执行游戏、修改器或包内命令，没有完成原引擎的反编译。

## 1. 结论

资源可以转换；完整玩法还需要重建运行时。当前最有价值的发现是：两个实际加载的 `.SO` 文件保留了可解析的函数符号表和字符串表，**502 条函数记录、193 个非零数字入口**可以定位。`MAGIC.INI` 的 **110 个武将技 SCRIPT 引用全部能连接到脚本入口**；这使技能迁移有了可追踪的起点，而不是只凭画面猜效果。

但符号表可读不等于脚本可执行。字节码指令集、系统调用、原生对象处理器、伤害与 AI 等算法还没有恢复。Web 版方案不能把“读取 PAK / 播放 SHP”当作“完整运行原游戏”。

建议采用 **数据转换 + 明确状态模型 + TypeScript 规则重写** 为主线；同步验证脚本格式，将能证明语义的技能脚本转换成受控的事件指令。先用有限技能样本决定是否值得实现完整脚本解释器，避免从一开始承担全部 VM 和 Win32 内存兼容工作。

## 3. EXE 与操作系统依赖

实测 PE 参数：机器类型 `0x014c`（x86）、PE32 `0x010b`、GUI 子系统、映像基址 `0x400000`、入口 RVA `0x6ed80`、映像大小 884,736 字节。

| 节 | 磁盘偏移 | RVA | 磁盘大小 | VirtualSize |
|---|---:|---:|---:|---:|
| `.text` | `0x400` | `0x1000` | 513,024 | 512,910 |
| `.rdata` | `0x7d800` | `0x7f000` | 6,656 | 6,424 |
| `.data` | `0x7f200` | `0x81000` | 152,064 | 338,390 |
| `.idata` | `0xa4400` | `0xd4000` | 4,608 | 4,144 |
| `.rsrc` | `0xa5600` | `0xd6000` | 5,120 | 4,844 |

上述地址由文件头直接读取。PE 时间戳不是可信的修正版发布日期，故不据此推断发行时间。

导入表包含以下平台依赖：

| 依赖 | 实际导入示例 | Web 迁移含义 |
|---|---|---|
| USER32 / GDI32 | `CreateWindowExA`、`DispatchMessageA`、`GetDC` | 窗口、消息和输入需替换为浏览器机制 |
| DDRAW | `DirectDrawCreate` | 原 2D 绘图后端需要替换 |
| DSOUND | `DirectSoundCreate` | 音效播放需适配 Web Audio 等机制 |
| WINMM | `timeGetTime`、`timeSetEvent`、`mciSendCommandA`、`waveOutSetVolume` | 时钟、音频与媒体接口需重建 |
| AVIFIL32 / MSVFW32 | `AVIFileOpenA`、`AVIStreamRead`、`ICDecompress` | EXE 有视频读取路径；是否在本包实际触发需另证，不能由导入推出本包包含所有影片 |
| ADVAPI32 / KERNEL32 | 注册表、文件、内存、进程及同步 API | 设置与存档需浏览器存储适配；进程地址不能直接搬进 JS |
| ole32 | `CoInitialize`、`CoCreateInstance` | 存在 COM 依赖，不适合仅重新打包成网页 |

**与英文补丁的兼容性限制**：英文补丁的 `tools/build_exe.py` 固定要求 SHA-256 为 `60F8AD...D9B2A26`，并注明其数据区磁盘偏移等于 RVA；本包 `.rdata`、`.data` 的磁盘偏移与 RVA 明显不同。`shim/dsound.c` 又包含固定的游戏函数地址、对象字段偏移和三组绘制跳转。虽然本 EXE 同样导入 DirectSound，但这不能证明英文补丁的内存修改地址可复用。

证据：`binary-summary.json → exe`；英文补丁 `tools/build_exe.py` 的 `EXE_SHA256`、`DATA`、`make_table()`；`shim/dsound.c` 的 `REROUTES` 及游戏函数地址。

## 4. `.SO` 脚本实际恢复到什么程度

### 4.1 已验证的结构

四个文件都以 `Smart Script` 加 NUL 填充构成 16 字节签名，后续头部到 `0x40`。以下是依据四个样本交叉验证的结构，不是完整格式规范：

| 偏移 | 观测值 / 结构 | 证据强度 |
|---|---|---|
| `0x10` | 四个文件均为 `0x100` | 字节确定；版本号解释仍是推测 |
| `0x14` | 四个文件均为 `0x40` | 指向首段内容；与最早函数偏移相符 |
| `0x18` / `0x1c` | 第一张表偏移 / 条目数 | 四个样本长度关系均成立 |
| `0x20` / `0x24` | 第二张表偏移 / 条目数 | 四个样本长度关系均成立 |
| `0x28` | 当前两个文件为 `0x79`；旧 SYSTEM 为 `2` | 含义未知，不命名为指令数或入口号 |
| `0x2c` | 第二张表结束位置 | 当前文件随后有编译器署名；旧文件恰好结束 |
| `0x30–0x3c` | 当前全 `0xffffffff`，旧文件全 `0` | 含义未知 |

第一张表每条 16 字节，四个 32 位小端值：`函数内容偏移 / 参数个数候选 / 名称字符串偏移 / 数字入口 ID`。第三个值全部指向合法 ASCII 标识符；第一个值全部是 4 字节对齐的表前偏移；非零数字入口均没有文件内重复。第二个值与符号命名及调用形态吻合，但参数数量仍需从字节码调用过程验证。

第二张表每条 4 字节，全部指向表前、以 NUL 结束的字符串；解码得到函数名、资源名、对白等。没有把它误记成重定位表。

| 文件 | 第一表偏移 | 函数记录 | 非零数字入口 | 字符串记录 | 第二表结束 |
|---|---:|---:|---:|---:|---:|
| 当前 SYSTEM | `0x4fb4` | 39 | 21 | 80 | `0x5364` |
| 当前 MAGIC | `0x3d548` | 463 | 172 | 580 | `0x3fb48` |
| 包内旧 SYSTEM | `0x42c8` | 29 | 20 | 41 | `0x453c` |
| 包内旧 MAGIC | `0x3d460` | 454 | 172 | 314 | `0x3f5a8` |

“包内旧文件”只表示 `.OLD` 文件名；没有证据证明它就是 Steam 版或未修改的官方原版。`SANGO.INI` 的 `[SCRIPT]` 只列出 `system.so`、`magic.so`，未列 `.OLD`。

### 4.2 入口与游戏功能的对应

SYSTEM 中可定位的数字入口包括：

| 符号 | ID | 可支持的迁移分析 |
|---|---:|---|
| `SearchTalk` / `ReportResult` | 5 / 6 | 搜索与结果呈现流程 |
| `ChildGenTalkNew` | 10 | 修正版新增的成年武将对话路径线索 |
| `LoadingBattleMap` / `StartBattle` | 50 / 51 | 战场加载与开战 |
| `EnterPolicy` / `EnterMapmode` | 52 / 53 | 内政与大地图阶段切换 |
| `EnterWarprep` / `EnterBattle` | 54 / 55 | 战前准备与战斗进入 |
| `BattleEndTalk` / `MajorDeath` | 56 / 57 | 战斗结算对白与主将死亡 |
| `EnterMapMoveCamera` / `AllRush` | 58 / 59 | 镜头与全军突击 |
| `KillGeneral` / `FreeGeneral` / `YieldGeneral` | 70 / 71 / 72 | 俘虏处置路径 |
| `WeatherObjectDeath` | 99 | 天气对象回调 |

这些符号说明该功能有脚本参与，不说明全部判定都写在脚本内。例如 `YieldGeneral` 可能仍调用 EXE 的归降判定；需要继续追踪调用。

`MAGIC.INI`：110 条 `[MAGIC]` 有互不重复的 `SCRIPT` 数字，全部在当前 MAGIC 符号表找到。例如 `SEQUENCE=2` 的“落月弓”使用 `SCRIPT=502 → Magic2`；而 `SEQUENCE=3` 的“地泉衝”使用 `SCRIPT=504 → Magic4`，`SEQUENCE=4` 的“火箭”使用 `SCRIPT=503 → Magic3`。编号顺序不可直接用 `[MAGIC].SEQUENCE + 500` 替代，必须保存显式映射。名称、序号和目标入口均可在 `magic-script-links.json` 逐条复核。

67 条 `[WISE]` 没有 `SCRIPT` 字段。军师技不能简单沿用武将技的脚本加载方式；其具体效果需从原生分派或运行行为继续定位。

### 4.3 版本差异与内存访问

当前 SYSTEM 相对包内旧 SYSTEM 多 10 个符号；当前 MAGIC 多 9 个符号，没有旧符号被删除。两者共同新增以下九个函数：

`GetByte_Old`、`GetByte_Signed_Old`、`GetShort_Old`、`GetShort_Signed_Old`、`GetInt_Old`、`SetInt_Old`、`SetShort_Old`、`SetByte_Old`、`SetString_Old`。

SYSTEM 额外新增 `ChildGenTalkNew`，ID 为 10。相同非零数字 ID 在新旧文件之间未发现名称冲突。首个辅助函数内容中能直接观察到 `0x004a6878` 等看似进程地址的常量，但本次没有确定它所指对象，不能把常量当作已识别字段。

这意味着即使恢复了 VM，也可能要实现旧式内存访问语义。推荐将已识别访问改写成 `readGeneralField` / `applyBattleEffect` 等受控游戏状态操作，而不是给 Web 解释器任意访问主机内存的能力。尚未识别的访问应明确报错，不应静默返回零。

## 5. 对象与动画不是纯图片列表

`THINGS.INI` 实际有 **621 个 `[OBJECT]` 段**，尽管头部 `TotalObjectDefine=300`；不能把头部宣称值直接当实际对象数量。`[DEFINE]` 声明了 **21 个 Process 常量**，例如士兵、主将、投射物、阴影、天气、马匹及武器处理器。

621 段对应 **620 个唯一 Sequence**。重复的 `17021` 位于标准化副本第 6685、6694 行，均名为“石頭上的火”，全部字段和 `Wait` 动作序列完全相同。导入时可以对这一个完全同义记录去重并保留两个来源位置；不能把这个案例推广为“所有同 ID 都允许后写覆盖”。不同内容的同 ID 应报告冲突，原引擎 first/last-wins 行为本次未验证。

实测 Process 引用中，`MagicObjectProcess` 348 次、`ForceMajorObjectProcess` 120 次、`ForceSoldierObjectProcess` 52 次、`MajorGeneralWeaponProcess` 34 次。另有 **1 个空 Process 值**，需要原加载器行为验证；导入器不得把下一行 `Directory` 误吞为它的值。

对象数据还包含：

- `Type`、`Space`、`FLAGS`：类型、空间参数、碰撞/目标/光效等位标志；具体字段单位仍需实测。
- `Directory` 和动作序列：待机、移动、攻击、死亡、受击、胜败等资源绑定。
- `#N`：序列中的数值控制标记；很可能影响停留/播放，但本次未证明精确时间单位。
- `@%OM_ATTACK`、`@%OM_DEATHSTOP` 等：事件标记。需要按原事件时序执行，不能只播帧。
- `!数字`：脚本回调。共 **15 次引用、9 个不同 ID**，全部找到当前脚本入口。
- `SCROVER` 等终止/控制词：精确控制流语义仍待确定。

9 个回调 ID 是 `99、6003、6004、7003、7004、7005、18002、33002、42002`，分别连接天气结束、飞箭、落石爆炸、发射器和炮击等符号。完整映射在 `binary-summary.json → animation_script_callbacks`。

**架构约束**：动画事件必须由游戏模拟时钟驱动，碰撞、攻击和脚本回调不能绑定浏览器实际渲染帧率。否则 30/60/144 Hz 显示器会改变战斗结果。

本次读取的 `SANGO.INI`、`MAGIC.INI`、`THINGS.INI`、`COMBINE.INI` 以 CP950 解码均无替换字符，SYSTEM 字符串表也可无损解码出繁体对白。这支持它们内部采用 Big5/CP950 的判断；包外简体说明文件使用 GBK，不能对整个游戏包统一猜编码，也不能从画面显示简体推出 INI 就是 GBK。

## 7. 下一阶段的可执行研究关卡

### G1：符号与调用引用闭合

1. 给两个在用 `.SO` 建立指令边界解析器，先从 `GetByte_Old`、简单对白、资源创建、短技能入口开始。
2. 对每条已识别指令保存偏移、操作数、栈效果；未知操作码显式列出，不跨越未知字节继续猜。
3. 验证所有跳转落到已识别指令边界、函数调用命中函数/数字入口、字符串引用落到已有表内。
4. 验收：选定样本不存在未解释指令，输出可复查反汇编；不以“字符串都读出来了”作为完成标准。

### G2：还原宿主调用和对象处理器

1. 在本版 EXE 中定位脚本执行分派与系统调用分派，记录函数地址与版本哈希。
2. 建立“编号 → 参数 → 返回值 → 改变的状态 → 证据”的表；重点覆盖生成对象、读取主将/士兵、伤害、随机数、延时、回调注册和对白。
3. 把内存访问辅助函数逐个落到已知状态字段；若未明，不开放任意虚拟地址读写。
4. 验收：基础技能样本所需宿主调用均有契约，未知调用会停止并报告，不会假成功。

### G3：最小技能与动画纵切验证

选择治疗、直线投射物、范围落雷、持续召唤/伏兵、附着特效各一个，额外测试 `!7003` / `!7005` 等动画回调。

记录原版在固定武将、兵种、兵数、地形、距离、技力下的消耗、受击对象、伤害序列、创建对象数量、生命周期和最终状态。随机性不能固定时，改比较分布与不变量，不谎称逐帧确定相等。

验收：先通过行为结果与事件顺序，再调特效视觉；不同渲染帧率下 Web 模拟结果相同。

### G4：军师技与修正版分歧

优先验证恢复技力、减缓集气、劝降、封武将技、化解计策、逼近/偷袭/包围等高风险项。`WISE` 无 SCRIPT 字段，所以必须额外追踪原生分派，不能把技能 VM 完成等同于军师技完成。Steam 参考文档与本包更新说明存在数值和行为差异时，以本包实测及锁定的规则配置为准。

### G5：决定 VM 投资规模

在 G1–G3 的结果基础上做一次可审查决策：若指令集小、宿主调用可稳定抽象且覆盖大部分技能，保留受限解释器；若大多数调用与 EXE 内存布局强耦合，转成 TypeScript 技能规格与事件时间线。两种路线都应保留源脚本入口和证据链接，便于对照修正。

该决策应在大量实现 110 个技能之前完成；否则最容易出现“图片很完整、战斗规则无法补齐”的返工。

## 8. 本次验证与限制

已验证四个脚本的表长度关系、所有符号/字符串指针范围、符号名合法性、代码偏移对齐、非零入口唯一性；完成全部 110 个武将技 SCRIPT 与 15 个动画回调的解析映射。PE 导入和节信息直接来自用户提供的 EXE。

未验证：原游戏实际运行时的指令执行、内存结构、系统调用契约、每个技能效果、所有军师技规则、AI 和旧存档格式。不能把本报告描述为已完整反编译游戏，也不能据此保证原版的逐帧复现。
